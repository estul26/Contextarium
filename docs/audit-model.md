# Audit Model

## Goal

Provide an append-only history of security- and state-relevant operations.

## Staged ownership

M2 introduces the minimum transactional mutation event required to guarantee that a revision-bearing accepted mutation never commits without its required audit linkage.

Because client authentication does not exist until M3, M2 records an explicitly identified **development/test actor** from the local development harness or internal call context. That attribution must remain labeled as development/test attribution and must not be represented as authenticated client identity.

From M3 onward, protected client-originated operations must record the authenticated client identity established by the authentication subsystem. M2-era events retain their original attribution and are not retroactively upgraded.

M6 completes the audit service: event vocabulary, access controls, query API, privacy/redaction rules, rejected/denied/failed-attempt behavior, and coverage tests.

## Required mutation event fields

For an accepted authoritative mutation, the event must include at least:

- event ID
- timestamp generated by the server
- actor identity plus attribution kind (`development_test` before M3 where applicable, `authenticated_client` from M3 onward)
- action
- resource type
- record/resource ID
- namespace when applicable
- revision identifier
- proposal identifier when applicable
- trusted request correlation ID generated/accepted under documented rules
- result
- bounded/redacted reason metadata when safe

The proposer and approver must remain distinguishable for proposal-originated changes.

## Example event names

```text
client.authenticated
record.created
record.updated
proposal.created
proposal.approved
proposal.rejected
proposal.conflicted
revision.restored
export.started
import.started
permission.denied
```

## Transaction rule

The required audit event for an accepted authoritative mutation commits in the same transaction as the revision/current-state change and proposal decision when applicable.

A terminal proposal conflict commits its proposal decision event in the same transaction as the `pending -> conflicted` transition and performs no record/revision mutation.

If a required event cannot be persisted, the corresponding authoritative mutation or terminal proposal decision must not commit.

Failed/denied operational attempts may require a separate event path because the main mutation transaction may roll back; M6 defines that behavior.

## Privacy

Audit logs should not duplicate full sensitive record payloads unless necessary.

Prefer identifiers, hashes, changed-field metadata, and concise reasons.

Client-provided request IDs, reasons, and provenance are untrusted metadata and must not be treated as authenticated identity.

## Integrity

Audit events are append-only at the application level. Ordinary API operations must not update or delete historical audit events.

This is not a cryptographically witnessed external ledger. A privileged database/host operator remains inside the trust boundary in v0.1.

## Access

Audit access requires an explicit scope and is considered sensitive because metadata can reveal user activity even without record payloads.
